# Smart Shift Management

מערכת שיבוץ משמרות לצוותי אבטחה, עם מנוע שיבוץ אוטומטי שמסביר כל החלטה שהוא מקבל.

**דמו חי:** https://shd-git-main-omergot5s-projects.vercel.app
בעמוד הפתיחה יש כפתור **"הפעל הדגמה"** — לחיצה אחת פותחת צוות עם 6 שומרים, שבוע משמרות והגשות זמינות אמיתיות, בלי הרשמה.

---

## מה הבעיה

אחמ"ש שמסדר משמרות ידנית צריך להחזיק בראש בו-זמנית: מי סימן שהוא לא זמין, מי עשה אתמול לילה ולא צבר 8 שעות מנוחה, מי כבר עבד 12 שעות רצוף, ומי מקבל בעקביות פחות משמרות מכולם. בפועל זה נגמר בגיליון אקסל, ובתחושת קיפוח אצל חצי מהצוות.

## מה המערכת עושה

בונה את הסידור אוטומטית, ומראה לאחמ"ש **למה** כל שומר נבחר — כך שהוא יכול לסמוך על התוצאה או לתקן אותה לפני שהיא מתפרסמת.

## מנוע השיבוץ

הקוד: [`src/lib/autoAssign.js`](src/lib/autoAssign.js)

### אילוצים קשיחים — פוסלים מועמד על הסף

| אילוץ | ברירת מחדל |
|---|---|
| זמינות שהשומר הגיש | מי שסימן "לא זמין" לא ישובץ, נקודה |
| מנוחה מינימלית בין משמרות | 8 שעות |
| מקסימום שעות רצופות | 12 שעות |
| חפיפה בין משמרות | אסור |
| תקרת משמרות שבועית | 6 |
| תקרת לילות שבועית | 3 |

אילוץ קשיח לא מנוקד — הוא פשוט מוציא את המועמד מהמשחק. לכן **המנוע לא מייצר שיבוץ שמפר חוק עבודה**; אם אי אפשר לאייש משמרת היא נשארת פתוחה עם הסבר מי נפסל ולמה.

### קריטריונים רכים — מדרגים את מי שנשאר

| קריטריון | משקל |
|---|---|
| סימן "זמין" (מול "אולי" / לא הגיש) | 40 |
| הוגנות עומס מול ממוצע הצוות | 35 |
| סבב לילות מול הממוצע | 22 (רק במשמרות לילה) |
| נוחות מנוחה מאז המשמרת הקודמת | 10 |
| רציפות סוג משמרת | 5 |
| כבר משובץ באותו יום | −12 |

הניקוד הסופי מוצג כאחוז התאמה — סכום הנקודות חלקי המקסימום האפשרי לאותה משמרת.

### איך זה עובד

1. **סדר מילוי** — המשמרות ממוינות לפי מידת הקושי, הכי מוגבלת קודם (`most-constrained-first`). לשבץ קודם את המשמרת שאף אחד לא רוצה, בזמן שעוד יש אופציות פתוחות.
2. **מילוי חמדני** — לכל תקן: סינון לפי אילוצים קשיחים, דירוג לפי הקריטריונים הרכים, בחירת המוביל.
3. **מעבר איזון** — חיפוש מקומי שמעביר משמרות מהשומר העמוס לפנוי, כל עוד זה לא מפר אילוץ.

**דטרמיניסטי** — אין `Math.random`. אותם נתונים תמיד מייצרים את אותו סידור, כולל שוברי שוויון. אפשר להריץ שוב ולקבל בדיוק את אותה תוצאה, וזה מה שמאפשר לסמוך על המערכת.

### בדיקות

```bash
node scripts/verify-scheduler.mjs
```

מריץ שבוע מלא ומוודא שכל אילוץ קשיח באמת נשמר בפלט, שהתוצאה דטרמיניסטית, שכל שיבוץ נושא הסבר, ושמקרי קצה (אין שומרים / אין משמרות / כולם לא זמינים) לא מפילים כלום.

```bash
node scripts/verify-backend.mjs
```

בודק מקצה לקצה מול Supabase אמיתי: הרשמת אחמ"ש, יצירת צוות, הצטרפות מאבטחים, הגשת זמינות, שיבוץ, פרסום, וכניסה חוזרת ממכשיר אחר — כולל אימות ש‑RLS באמת חוסם מאבטח מלערוך משמרות או לשנות זמינות של מישהו אחר.

## הרשאות וגישה

| | אחמ"ש | מאבטח |
|---|---|---|
| כניסה | אימייל + סיסמה (Supabase Auth) | קוד צוות + שם, בלי סיסמה |
| יצירת ועריכת משמרות | ✅ | ❌ |
| שיבוץ ופרסום | ✅ | ❌ |
| הגשת זמינות | ✅ | רק של עצמו |
| צפייה בסידור | ✅ | רק אחרי פרסום |

הכל נאכף ב-Row Level Security ברמת מסד הנתונים, לא בקוד הלקוח. מאבטח נכנס כמשתמש אנונימי אמיתי (`signInAnonymously`) ומקבל זהות שה-RLS יכול להגן עליה — כך שהוא לא צריך לזכור סיסמה, אבל גם לא יכול לגעת בנתונים של אחרים.

טבלאות: `gs_teams`, `gs_profiles`, `gs_shifts`, `gs_assignments`, `gs_availability`, `gs_swap_requests`, `gs_tasks`.

## הרצה מקומית

```bash
npm install
npm start
```

האפליקציה מצביעה על פרויקט Supabase קיים כברירת מחדל. כדי להצביע על פרויקט אחר:

```bash
# .env.local
VITE_SUPABASE_URL=https://<project>.supabase.co
VITE_SUPABASE_ANON_KEY=<publishable-key>
```

בפרויקט Supabase חדש צריך להדליק ב‑Authentication → Providers:
- **Anonymous sign-ins** — כניסת מאבטחים בקוד צוות
- לכבות **Confirm email** — אחרת אחמ"ש חדש תקוע עד אימות מייל
